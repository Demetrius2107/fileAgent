
  当前系统不是让大模型直接读取 Excel，也不是把整份文档直接塞给大模型，而是分成两个阶段：

  上传阶段：文件 -> 解析 -> 分块 -> 向量化 -> 写入 Elasticsearch

  聊天阶段：问题 -> 检索 -> 融合排序 -> 恢复完整上下文
                -> 拼 Prompt -> Chat 模型生成答案

  ## 一、上传文档到知识库

  入口在 fileagent-document/src/main/java/com/demetrius/fileagent/document/application/RagFileAppServiceImpl.java:74。

  ### 1. 先向 H2 保存文件记录

  系统先保存一条 PARSING 状态的记录：

  H2 rag_file
  - id
  - 知识库名称
  - 标签
  - 文件名
  - 文件大小
  - 状态
  - 分块数量

  必须先保存，是因为要让 H2 生成真实的 fileId。后面的每条 ES 数据都带这个 fileId，这样才能按文件查询和删除。

  这里可以理解为：

  - H2 管理“这个文件的处理状态”
  - Elasticsearch 管理“这个文件里可检索的知识”

  ### 2. 将上传文件写入临时文件

  Multipart 文件先写入临时目录，然后根据 MIME 类型选择对应解析器。处理完成后临时文件会删除。

  当前代码实际上没有长期保存源文件。企业版后续通常会把原文件放到 MinIO、OSS 或 S3，H2/MySQL 只保存对象地址。

  ### 3. Excel 结构化解析

  Excel 解析在 fileagent-document/src/main/java/com/demetrius/fileagent/document/infrastructure/ExcelDocumentParser.java:72。

  处理逻辑是：

  1. 跳过隐藏 Sheet。
  2. 读取公式计算后的值。
  3. 处理合并单元格。
  4. 用空行划分连续数据区域 section。
  5. 识别区域表头。
  6. 将每一行序列化成带字段名的文本。
  7. 为同一区域的行设置相同 parentId。

  例如 Excel 原始行：

  Objective | O1
  目标描述   | 提升系统稳定性
  权重       | 30%

  会变成更适合检索的文本，而不是没有语义的单元格数组。

  这套方法没有硬编码 Objective 1、KR 1 等业务正则。它根据 Excel 的通用版面结构切分，所以不仅能处理 OKR，也能处理制度表、项目计划、人员清单等表格。

  ### 4. 建立父子分块

  父子块生成在 fileagent-document/src/main/java/com/demetrius/fileagent/document/application/RagFileAppServiceImpl.java:126。

  系统保存两种 ES 文档：

  - CHILD：一行或者一个较小知识单元，用于检索。
  - PARENT：一个连续区域内所有子块的完整内容，用于回答。

  这是本次效果提升的核心。

  section-3 父块
  ├── O1 子块
  ├── KR1 子块
  ├── KR2 子块
  ├── O2 子块
  └── KR1 子块

  小块容易精确命中“大模型工具”“O1”“系统稳定性”等词，但单独一个小块可能不完整。父块包含完整区域，适合交给大模型总结“所有 O”。

  所以我们采用：

  用小块查得准
  用父块答得全

  ### 5. 子块向量化

  向量化在 fileagent-document/src/main/java/com/demetrius/fileagent/document/infrastructure/ElasticsearchKnowledgeIndexRepository.java:64。

  分块和向量模型是两件不同的事：

  - 分块决定“知识被切成什么单位”。
  - Embedding 决定“怎么比较问题和知识的语义相似度”。

  例如：

  问题：饶赛杰今年要提升哪些技术能力？
  文档：主动学习并使用 AI 编程工具提升开发效率

  文字不完全相同，但 Embedding 向量距离可能很近，因此 KNN 能召回它。

  只有 CHILD 生成向量，PARENT 不生成。因为父块不参与首次召回，只在命中子块后按 parentId 获取。这样可以减少向量接口调用、索引空间和长文本限制问题。

  通义每批最多 20 条，当前配置每批 10 条，避免之前的批量大小报错。

  ### 6. 批量写入 Elasticsearch

  ES 字段映射见 fileagent-document/src/main/java/com/demetrius/fileagent/document/infrastructure/ElasticsearchKnowledgeIndexInitializer.java:47。

  每条知识大致包含：

  chunkId、fileId、filename
  ragName、knowledgeTag
  content、embedding
  sheetName、sectionId、rowIndex
  parentId、chunkType、metadata

  content 用于关键词检索，embedding 用于语义检索，其他字段用于过滤、追踪来源和恢复父块。

  全部写入成功后，H2 状态改成 SUCCESS。失败时删除该 fileId 已写入的 ES 数据，并把 H2 状态改成 FAILED。

  ## 二、聊天时怎样召回知识

  聊天编排入口是 fileagent-chat/src/main/java/com/demetrius/fileagent/chat/application/ChatAppServiceImpl.java:64。

  ### 1. 读取历史并改写追问

  fileagent-chat/src/main/java/com/demetrius/fileagent/chat/application/RagQueryRewriter.java:32 只在存在历史用户消息时调用模型。

  例如：

  上一轮：2026 年饶赛杰的 OKR 有哪些？
  这一轮：那他的 O 呢？

  改写成：

  2026 年饶赛杰的 OKR 中有哪些 Objective？

  这样检索系统不需要理解“那”“他的”指什么。改写失败会直接使用原问题，不会阻断聊天。

  旧的 RagRetrievalPlanner 已删除。企业知识库聊天本来就应该稳定执行检索，让模型判断“要不要检索、用什么模式”会增加一次模型调用，还可能把年份、O/KR 或检索方向判断错。

  ### 2. BM25 关键词召回

  混合检索在 fileagent-document/src/main/java/com/demetrius/fileagent/document/infrastructure/KnowledgeSearchPortImpl.java:52。

  BM25 擅长匹配：

  - 人名：饶赛杰
  - 年份：2026
  - 编号：O1、Objective 2
  - 文件名、Sheet 名和专业术语

  这是纯向量检索容易遗漏的精确文本信号。

  ### 3. KNN 向量召回

  系统把用户问题也交给同一个 Embedding 模型，得到 1024 维查询向量，然后让 Elasticsearch 查找距离最近的子块。

  必须使用相同的 Embedding 模型和维度，因为查询向量与文档向量只有处在同一个向量空间里才能比较。

  大模型不会看到这些向量。向量只负责“找文本”，最终交给 Chat 模型的仍然是正常文字。

  ### 4. RRF 融合两路结果

  fileagent-document/src/main/java/com/demetrius/fileagent/document/infrastructure/RrfFusion.java:21 将 BM25 和 KNN 排名融合。

  不能直接把两边分数相加，因为 BM25 分数和余弦相似度不是同一个量纲。RRF 只使用名次：

  RRF 分数 = 1 / (常数 + 排名)

  某个子块如果在关键词和向量两路都排名靠前，融合后就会得到更高排名。

  ### 5. 可选 Reranker

  fileagent-document/src/main/java/com/demetrius/fileagent/document/infrastructure/DashScopeKnowledgeReranker.java:31 会让 qwen3-rerank 对候选文本进行更精细的相关性判断。

  区别是：

  - Embedding：速度快，适合从大量数据中初筛。
  - Reranker：判断更细，适合给几十个候选重新排序。
  - Chat 模型：读取最终资料并组织答案。

  Reranker 默认关闭，配置缺失或调用失败会降级到 RRF，不影响主流程。配置位于 fileagent-starter/src/main/resources/application.yml:61。

  ### 6. 命中子块后恢复父块

  混合排序选出前 12 个子块后，系统根据 parentId 使用 ES mget 一次性读取对应父块。

  比如真正命中的是 O3 的一行，但用户问“所有 O”，最终给大模型的不是只有 O3，而是 O3 所属完整表格区域。多个子块属于同一父块时还会去重，避免重复占用模型上下文。

  ### 7. 拼接 Prompt 并生成答案

  fileagent-chat/src/main/java/com/demetrius/fileagent/chat/application/RagPromptBuilder.java:41 把以下内容拼成最终 Prompt：

  System 回答规则
  + 最近的聊天历史
  + 检索到的父块正文与文件、Sheet 来源
  + 用户原始问题

  注意：用于检索的是“改写后的独立问题”，展示和回答的仍是用户原始问题。

  最后 Chat 模型流式返回答案，系统保存 Assistant 消息，并通过 SSE 返回来源文件和完成事件。

  一句话总结

  当前方案的本质是：

  结构化小块提高召回精度
  + BM25 保证专有名词和编号
  + 向量检索补足语义表达差异
  + RRF 合并两种召回能力
  + Reranker 提升候选排序精度
  + 父块恢复完整上下文
  + Chat 模型只负责基于资料组织答案

  这已经是一条标准的企业 RAG 基础链路。下一阶段真正需要补的是原文件对象存储、异步索引任务、索引版本切换、权限过滤、召回评测集和可观测性，而不是继续依靠 Prompt 修补检索问题。
