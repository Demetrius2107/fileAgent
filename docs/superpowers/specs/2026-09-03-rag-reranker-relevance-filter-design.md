# RAG Reranker 相关性过滤设计

## 目标

- 在 reranker 成功返回后过滤低相关性知识片段。
- Prompt 与 SSE `sources` 使用同一份过滤后结果，避免展示未参与回答的低相关文件。
- 增加 reranker 与多轮问题改写的诊断日志，便于观察分数、耗时和降级行为。
- 保持现有多轮策略：第一轮不改写，第二轮起每轮调用模型生成独立检索问题。

## 范围

本次只修改检索与日志链路，不实现以下能力：

- 文件 SHA-256 去重。
- 知识文件删除接口。
- H2 与 Elasticsearch 周期性全量对账任务。
- 原始文件持久化。

上述文件生命周期能力由其他开发任务负责，避免修改相同的上传和持久化代码。

## 相关性过滤

在 `DashScopeKnowledgeReranker` 成功取得排序结果后，按新的
`fileagent.reranker.min-relevance-score` 配置过滤结果，默认值为 `0.2`。

过滤发生在父块展开之前。`KnowledgeSearchPortImpl` 收到的结果已经完成过滤，
因此后续父块展开、Prompt 构造和 SSE 来源汇总天然使用同一份命中结果，不再增加第二套来源判断。

reranker 未启用、配置缺失、调用异常或响应无效时，保持现有 RRF 降级行为，
不使用 reranker 阈值过滤。RRF 分数是名次融合分数，与 reranker 相关性分数不在同一量纲。

阈值范围限制为 `0.0` 到 `1.0`。配置越高，误召回越少，但漏召回风险越高。

## 日志

reranker 使用 DEBUG 日志记录：

- 查询文本、候选数、实际提交数、`topN`、最低相关性阈值。
- 每条返回结果的排名、`chunkId`、文件名、分数以及是否保留。
- 返回数、保留数、过滤数和总耗时。

日志不记录知识片段正文、API Key 或请求头。

`RagQueryRewriter` 保持现有调用条件，补充 DEBUG 日志：

- 第一轮跳过改写。
- 原问题、改写后问题和模型调用耗时。
- 失败降级时的原问题、耗时和失败原因。

## 历史孤儿索引

当前确认的 `fileId=15` 是 Elasticsearch 中的旧版孤儿索引，H2 已无对应记录；
`fileId=18` 是当前有效记录。此次只采用一次性、精确的 `fileId=15` 删除操作，
不增加定时扫描任务，也不进行在线全表扫描。

长期一致性应由业务写路径保证：上传失败按 `fileId` 回滚索引，用户删除时先删除
Elasticsearch 索引再删除 H2 元数据。历史对账如未来确有需要，应采用离线、分页、
限速任务，而不是高频全量扫描。

## 验证

- reranker 成功时，低于阈值的结果被过滤，等于阈值的结果保留。
- reranker 关闭、缺少配置、返回空结果或调用异常时继续返回 RRF 候选。
- 所有结果均低于阈值时返回空命中，聊天链路按知识未命中处理，`sources` 为空。
- `KnowledgeSearchPortImpl` 的父块展开和 `finalTopK` 行为保持不变。
- 第一轮问题不调用改写模型，第二轮及以后仍调用，失败时回退原问题。
- 运行相关模块测试及 Maven 全量测试。
